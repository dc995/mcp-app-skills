# VS Code MCP App image sharing validation - July 2026

**Evidence type:** empirical

## Environment

- Date: 2026-07-24
- Host: VS Code Insiders 1.131.0-insider
- Host commit: `9aab2f51076649ada9d3d8412558fd1484dd5f04`
- OS: Windows x64, build 26100
- MCP Apps SDK: `@modelcontextprotocol/ext-apps` 1.7.4
- MCP SDK: `@modelcontextprotocol/sdk` 1.29.0
- Probe: Cobalt Canvas image studio

The exact embedded Chromium/Electron versions were not captured. Revalidate this
result when the host or MCP Apps SDK changes.

## PNG clipboard write

The app resource declared `_meta.ui.permissions.clipboardWrite`. After the user
clicked **Copy Image**, the app converted an `image/png` data URL to a `Blob` and
called:

```typescript
await navigator.clipboard.write([
  new ClipboardItem({ "image/png": blob }),
]);
```

The promise resolved and the PNG bitmap was available to paste/attach outside the
app. This proves the direct-user-gesture PNG path in the environment above. It
does not prove background clipboard writes, other MIME types, or future VS Code
builds.

`app.getHostCapabilities()?.sandbox?.permissions` was still not populated. Apps
therefore cannot treat an absent `sandbox.permissions.clipboardWrite` value as a
reliable negative signal in this host. Feature-detect `navigator.clipboard.write`
and `ClipboardItem`, perform the write inside the click handler, catch rejection,
and retain a text or artifact-path fallback.

## App-to-chat image message

`app.getHostCapabilities()?.message?.image` was not advertised, so the probe
disabled its **Add to chat** action and did not call `app.sendMessage()` with image
content. Direct MCP App-to-chat image delivery was not validated. An image later
visible in chat may have arrived through a manual clipboard paste and is not
evidence that `ui/message` image delivery succeeded.

Apps should capability-gate this path and keep it separate from clipboard copy:

```typescript
const canSendImage = Boolean(app.getHostCapabilities()?.message?.image);
```

## Sampling authorization

- Date: 2026-07-31
- Evidence type: empirical comparison
- Host: VS Code Insiders
- Host build: not captured; revalidate before generalizing to later builds
- MCP SDK: `@modelcontextprotocol/sdk` 1.29.0
- Probes: one MCP App with a working UI-initiated sampling button and one
  equivalent app without a per-server sampling grant

Both apps used `app.callServerTool()` from the MCP App UI and then issued
`sampling/createMessage` from the server. Both negotiated the sampling
capability, and stdio provided a bidirectional transport. The working workspace
also configured:

```json
{
  "chat.mcp.serverSampling": {
    "<configured-server-entry>": {
      "allowedOutsideChat": true
    }
  }
}
```

Without that grant, VS Code returned a schema-valid sampling result with
`stopReason: "cancelled"`. Adding the exact server entry permission and
reconnecting the MCP server enabled the outside-chat path. This establishes
three independent requirements for UI-initiated sampling: a bidirectional or
session-bound transport, negotiated sampling capability, and host authorization.

Scope: this result covers MCP App button actions in VS Code. Other hosts and
future VS Code builds may use different policy surfaces. Direct-chat sampling
authorization was not exercised by this probe.
